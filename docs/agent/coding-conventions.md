# 编码约定

## 通用原则

- 延续现有模块风格：代码直观、顺序可读、命名保留业务语义，避免无关重构。
- 使用卫语句减少明显的嵌套，但不要为此破坏线性可读性。
- 注释保持稀少，只解释代码无法直接表达的原因、外部限制或时序要求。
- TypeScript 保持严格类型；使用现有类型、Zod schema 和 `satisfies` 风格，而非用宽泛断言绕过类型检查。

## React 与状态

- 函数组件与 hooks 是现有 React 代码的常用形态。
- 卡片更新经 `useCardStore` action 完成，避免在组件或 Agent 工具中原地修改卡片。
- 异步 UI 操作保持错误可见，并通过既有状态/翻译路径向用户报告；不要吞没可诊断错误。
- 大型资源和大型世界书编辑器遵循现有延迟挂载与轻量摘要模式，避免将长 data URI 直接放入常驻受控输入。

## 领域与兼容性

- 修改 CCv3 schema、迁移或世界书字段时，保留未知字段与扩展字段。
- 共享卡片规则需同步审查前端和 Rust 的 schema、迁移和校验实现。
- Agent 变更保持“权限 → 类型化语义提案 → 当前状态检查 → 用户确认 → store action”边界；不要引入通用 JSON Patch 或绕过确认的写入。

## Rust

- Rust 模块使用小型职责明确的函数和 `Result` 错误传播，Tauri command 保持为领域函数的薄包装。
- 文件格式与校验行为变更应补充同模块单元测试，并避免改变不相关的导入导出兼容性。

仓库未配置可据实引用的 lint 或 formatter 命令；新增工具链前不要将假定的命令写入文档或自动化。
